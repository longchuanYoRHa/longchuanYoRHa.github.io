AERO62520 Project: Leo Rover pick and place robot

Team Repository on GitHub

Project Overview

prototype of the rover

The goal is an autonomous rover that can explore unknown terrain, detect target blocks with computer vision, grasp them with an integrated manipulator, and deliver payloads to designated collection points — bringing together SLAM-based localization, Nav2 navigation, inverse kinematics for the arm, and a mechanically stable payload on the Leo Rover 1.8 platform.

My Role and Contributions

Shaotong Hong led Software Design for the FDR documentation and owned the navigation and software-integration thread on the project plan — from Nav2 bringup and exploration strategy work through simulation and hardware tests, Action-oriented explore-node integration, and arm–camera–NUC–rover integration (with teammates).

Central control and system software

The robot is exploring the environment

  • Authored the software design narrative for the FDR: system software block diagram, central control state machine on the NUC, and alignment with live RQT graphs during operation.
  • The task-oriented FSM (e.g. EXPLORE, GRASP, PLACE_IN_BIN, navigation-to-object / pre-place states) coordinates asynchronous perception, navigation completion, and arm status; it includes robustness measures such as interest-point blacklisting on timeout and distinct logic for loaded vs. unloaded operation.

Vision stack context (team subsystem; documented in FDR)

Team 12

The report’s vision section (benchmarking and implementation) is part of the integrated software story I helped tie to the rest of the stack:

  • Model selection: weighted comparison of YOLOv8n, YOLO11n, and RT-DETR-L; YOLO11n was chosen for the best balance of speed (~58 FPS), accuracy, and resource use on the NUC.
  • Inference: OpenVINO with intel:gpu, 640×480 input, and high confidence threshold to limit false positives.
  • Spatial reasoning: RealSense D435i depth aligned to color, 3D deprojection, and width-based categorization (e.g. cube vs. bin).
  • Safety and modularity: topic routing by color/size namespaces and a MAX_Z_LIMIT gatekeeper so targets stay within the MyCobot 280 Pi workspace.

Navigation and integration

  • Nav2 + SLAM (slam_toolbox) pipeline on the NUC with RPLidar A2M12; exploration strategy evaluation (frontier / coverage, m-explore-ros2 suitability) and integration tests on simulation and real hardware.
  • Explore node extended with an Action interface for orchestration and interrupt/cancel behaviour, integrated with bringup and tested under external interrupt scenarios.
  • Joint integration: arm–camera–NUC–rover together with Qikai Sun to close the loop from perception to base motion and manipulation.

Technical Highlights

  • Robot platform: Leo Rover 1.8 + Intel NUC + MyCobot 280 Pi + RealSense D435i + RPLidar A2M12
  • Middleware: ROS2, Nav2, slam_toolbox, FastDDS XML hardening (as described in the FDR cyber-security section)
  • Perception: YOLO11n via OpenVINO (GPU), spatial validation and topic routing
  • Mission logic: FSM-style central controller (task_manager) coordinating explore, vision, and arm nodes
  • Power: 2× Anker Prime 26K USB-C PD delivery to NUC and manipulator (major mass reduction vs. earlier baseline, per report)
  • Languages / tooling: Python, C++ where applicable, RQT for runtime graph verification

Reflection

Working through this FDR deepened my experience with end-to-end autonomous mobile manipulation: not only Nav2 and exploration on a real rover, but also how perception outputs, state machines, and manipulator commands must stay modular, verifiable, and safe under timing and power constraints. Aligning design diagrams with live RQT topology and requirements verification made the difference between a “collection of nodes” and a mission-ready system architecture.

“A field robot is only as trustworthy as the glue between its map, its pixels, and its states.”
